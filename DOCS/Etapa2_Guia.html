Alínea da ficha
3.a
Ação

Como lá chegar

O que vamos fazer. Pedir ao Entity Framework que compare as classes com a última migration e escreva, num ficheiro C#, as instruções para pôr a base de dados igual às classes.

Add-Migration BDInicial

A consola mostra Build started... e Build succeeded., porque o comando começa por compilar o projeto. No fim aparece To undo this action, use Remove-Migration. e o Visual Studio abre o ficheiro da migration que acabou de criar.

Porquê. O Add-Migration faz quatro coisas, por esta ordem:

  1. compila o projeto (se houver erros, pára aqui com Build failed.);
  2. constrói o modelo a partir do ApplicationDbContext: os doze DbSet, as classes da pasta Entities, o ApplicationUser, as relações do OnModelCreating e as tabelas que o IdentityDbContext traz;
  3. compara esse modelo com a fotografia guardada na última migration (o ficheiro ApplicationDbContextModelSnapshot.cs), ou com um modelo vazio, se ainda não houver migrations;
  4. escreve as diferenças como código C#, num ficheiro novo, e atualiza a fotografia.

Não toca na base de dados. Nesta altura a MyHotelsPWeb continua a não existir.

O nome BDInicial é escolhido por nós, e é o da ficha: identifica a migration e deve dizer o que ela faz.

FicheiroO que éMexe-se nele?
<data>_BDInicial.csA migration: o método Up aplica as alterações (cria tabelas, acrescenta colunas) e o método Down desfá-lasNão
<data>_BDInicial.Designer.csInformação interna do Entity Framework sobre esta migrationNão
ApplicationDbContextModelSnapshot.csA fotografia do modelo depois desta migration. É com ela que o próximo Add-Migration vai compararNão

<data> é a data e a hora em que o comando correu, no formato AAAAMMDDhhmmss (por exemplo 20261118101532_BDInicial.cs). É o que mantém as migrations por ordem.

O Add-Migration corre o Program.cs só até à linha var app = builder.Build();, para saber como o contexto é configurado. O bloco dos dados iniciais (alínea 3.k da Etapa 1) fica depois dessa linha e não é executado: é por isso que o comando funciona, apesar de a aplicação não arrancar.

Atenção. Correr o comando uma única vez. Se for corrido de novo, o Visual Studio responde que o nome BDInicial já é usado por uma migration. Se for preciso refazer a migration, a forma certa está na secção 3. Em grupo, só uma pessoa corre o Add-Migration; os outros recebem os ficheiros pelo repositório e correm apenas o Update-Database.

O que vamos fazer. Executar a migration: criar a base de dados MyHotelsPWeb no LocalDB, com todas as tabelas.

Update-Database

A resposta, no projeto criado para SQL Server LocalDB:

Build started...
Build succeeded.
Applying migration '00000000000000_CreateIdentitySchema'.
Applying migration '20261118101532_BDInicial'.
Done.

No projeto criado para SQLite falta a linha da CreateIdentitySchema. A data na linha da BDInicial é a de cada um.

Porquê. O Update-Database usa a connection string do appsettings.json (a DefaultConnection da alínea 3.e da Etapa 1) e faz o seguinte:

  1. liga-se ao servidor (localdb)\mssqllocaldb e, como a base de dados MyHotelsPWeb não existe, cria-a;
  2. cria a tabela __EFMigrationsHistory, onde o Entity Framework regista as migrations já aplicadas;
  3. compara as migrations do projeto com as que estão registadas nessa tabela, e executa as que faltam, por ordem de data;
  4. regista cada migration aplicada na __EFMigrationsHistory.

Por isso, correr o comando outra vez não faz mal: responde No migrations were applied. The database is already up to date. e não altera nada.

Nota. A base de dados fica guardada em dois ficheiros, MyHotelsPWeb.mdf (os dados) e MyHotelsPWeb_log.ldf (o registo de transações), na pasta do utilizador do Windows (C:\Users\<utilizador>\). Não se mexe neles diretamente: quem os gere é o LocalDB. Cada elemento do grupo tem a sua base de dados, na sua máquina; o que se partilha no repositório são as migrations.

Atenção. Se o comando parar com Introducing FOREIGN KEY constraint ... may cause cycles or multiple cascade paths, falta alguma das linhas OnDelete(DeleteBehavior.Restrict) do OnModelCreating (Etapa 1, alínea 3.c, passo 2). Corrigir o contexto e refazer a migration pela secção 3.2.

Verificar. A consola termina com Done. e não mostra linhas a vermelho. Se aparecer um erro, ver a secção 4.3.

3. Quando a base de dados não sai certa

Se a alínea 3.d mostrar diferenças, o erro está nas classes ou no contexto da Etapa 1, e não na base de dados. Corrige-se o código e refaz-se a migration. A forma de a refazer depende de o Update-Database já ter sido executado.

3.1 Antes do Update-Database

A migration foi criada mas ainda não foi aplicada (por exemplo, a verificação do passo 3.a falhou):

Remove-Migration

Depois, corrigir as classes, compilar, e voltar a correr Add-Migration BDInicial.

Porquê. O Remove-Migration apaga a última migration e repõe a fotografia (ApplicationDbContextModelSnapshot.cs) como estava antes dela. Apagar os ficheiros à mão não chega: a fotografia ficava com o modelo errado, e a migration seguinte saía incompleta.

3.2 Depois do Update-Database

A migration já foi aplicada e a base de dados existe. Primeiro apaga-se a base de dados, depois a migration:

Drop-Database
Remove-Migration

O Drop-Database pede confirmação antes de apagar: responder que sim. Depois, corrigir as classes, compilar, e voltar a correr os dois comandos:

Add-Migration BDInicial
Update-Database

Porquê. O Remove-Migration recusa apagar uma migration que já está aplicada na base de dados (a mensagem diz has already been applied to the database). Depois de apagada a base de dados, a migration deixa de estar aplicada e já pode ser removida.

Atenção. No projeto criado para SQL Server LocalDB, o Remove-Migration só remove a última migration, a BDInicial. A 00000000000000_CreateIdentitySchema fica, e é assim que deve ser. Não a apagar.

Nota. Isto só se faz agora, enquanto a base de dados não tem dados que interessem. Mais tarde, para alterar uma base de dados com dados, cria-se uma migration nova (Add-Migration com outro nome) e aplica-se com Update-Database, sem apagar nada. É o que acontece na Etapa 3.

3.3 O que não fazer

  • Alterar tabelas ou colunas no designer do Visual Studio: a base de dados deixa de corresponder às classes e às migrations.
  • Editar os ficheiros da pasta das migrations à mão.
  • Apagar ficheiros de migrations no Gerenciador de Soluções em vez de usar Remove-Migration.
  • Em grupo: duas pessoas a gerar migrations ao mesmo tempo. Uma gera e envia para o repositório; as outras recebem e correm Update-Database.
