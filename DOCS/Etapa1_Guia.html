0. Antes de começar

0.1 O que vamos construir

A Etapa 1 arranca a aplicação Gestão de Hotéis, a aplicação de gestão do trabalho prático MyHotels. Corresponde à ficha 3 das aulas laboratoriais: os passos são os mesmos, pela mesma ordem e com a mesma numeração (1.a, 1.b, 3.a a 3.o). Muda o tema, e por isso mudam as classes: em vez de uma loja com produtos, uma empresa com unidades hoteleiras, alojamentos e reservas.

É uma Blazor Web App que serve de backoffice da empresa: é nela que administradores e funcionários gerem as unidades hoteleiras, os alojamentos, as categorias, os regimes alimentares e as campanhas, e mais tarde as reservas e os utilizadores. Fala diretamente com a base de dados, sem passar pela API. As outras duas aplicações do enunciado (a API RESTful e a aplicação frontend MyHotels) ficam para as etapas que acompanham as fichas seguintes.

A aplicação de gestão é feita em três etapas, cada uma a acompanhar uma ficha das aulas:

2. Relações entre entidades (etapa 2 da ficha)

A etapa 2 da ficha é teórica: apresenta o vocabulário das relações no Entity Framework Core e quatro convenções para escrever uma relação de um para muitos (1-N). O MER do MyHotels precisa também das relações 1-1 e N-M, que a ficha deixa para mais tarde. A explicação completa, com diagramas, está nos slides desta etapa. Para executar as alíneas 3.b a 3.d basta reter o seguinte.

Relações 1-N. Numa relação 1-N, por exemplo "uma unidade hoteleira tem muitos alojamentos":

  • a entidade principal é a do lado 1 (Hotel);
  • a entidade dependente é a do lado N (Alojamento), e é na tabela dela que fica a chave estrangeira (HotelId);
  • uma propriedade de navegação é uma propriedade C# que aponta para a entidade relacionada: de referência quando aponta para um objeto (alojamento.hotel), de coleção quando aponta para muitos (hotel.alojamentos).

As quatro convenções da ficha diferem no que se escreve nas classes:

ConvençãoNa entidade dependenteNa entidade principal
1navegação de referêncianada
2nadanavegação de coleção
3navegação de referêncianavegação de coleção
4chave estrangeira e navegação de referêncianavegação de coleção

As relações 1-N do MyHotels usam a convenção 4, como ModoEntrega e Produto na ficha 3: chave estrangeira e navegação de referência no dependente, coleção no principal. Quando não se navega do principal para os dependentes (do utilizador para as suas reservas, por exemplo), a coleção não se escreve: as reservas de um cliente encontram-se com uma consulta a Reservas. É a convenção 1, com a chave estrangeira.

Relações N-M. Um alojamento oferece vários regimes alimentares, e cada regime é oferecido por vários alojamentos. Numa base de dados relacional isto precisa de uma terceira tabela, a tabela de ligação, com uma linha por cada par (alojamento, regime). No EF Core basta escrever uma navegação de coleção de cada lado: o EF Core cria sozinho a tabela de ligação, sem nenhuma classe a mais no projeto.

Relações 1-1. Uma unidade hoteleira tem exatamente uma morada, e essa morada não é de mais ninguém. Escreve-se como uma 1-N vista do lado dependente (chave estrangeira e navegação de referência em Hotel), e diz-se ao EF Core que é 1-1 no OnModelCreating, com WithOne() (alínea 3.c). Quando as duas classes têm navegação de referência uma para a outra (Pagamento.reserva e Reserva.pagamento), o EF Core reconhece o 1-1 sozinho.

// Uma morada. A mesma classe serve as unidades hoteleiras, os utilizadores
// e as reservas (a morada de faturação), cada um com a sua própria linha.
// Cada objeto desta classe corresponde a uma linha da tabela Moradas.

    // Chave primária, atribuída pela base de dados.

    [Required]
    [RegularExpression(@"^\d{4}-\d{3}$", ErrorMessage = "O código postal deve estar no formato '1234-567'.")]
    public string? CodigoPostal { get; set; }

    // Localidade: obrigatória, até 100 caracteres.
    [StringLength(100)]
    [Required]
    public string? Localidade { get; set; }

    // Distrito: obrigatório, até 100 caracteres.
    [StringLength(100)]
    [Required]
    public string? Distrito { get; set; }

    // País: obrigatório, até 100 caracteres. Começa preenchido com Portugal.

public class ApplicationDbContext(DbContextOptions<ApplicationDbContext> options) : IdentityDbContext<ApplicationUser>(options)
{
    // Registo das nossas entidades no contexto. Cada DbSet passa a ser uma tabela
    // da base de dados, com o nome da propriedade: Moradas, Hoteis, Categorias, ...
    // É também por aqui que se leem e gravam os dados, por exemplo context.Hoteis.
    public DbSet<Morada> Moradas { get; set; }
    public DbSet<Hotel> Hoteis { get; set; }
    public DbSet<Categoria> Categorias { get; set; }
    public DbSet<Caracteristica> Caracteristicas { get; set; }
    public DbSet<ModoDisponibilizacao> ModosDisponibilizacao { get; set; }
    public DbSet<RegimeAlimentar> RegimesAlimentares { get; set; }
    public DbSet<Alojamento> Alojamentos { get; set; }
    public DbSet<Campanha> Campanhas { get; set; }

    public DbSet<LinhaReserva> LinhasReserva { get; set; }
    public DbSet<Pagamento> Pagamentos { get; set; }
    public DbSet<Fatura> Faturas { get; set; }

    // As relações que as convenções não resolvem sozinhas.
    // OnModelCreating é o método onde se configura o modelo por código (Fluent API).
    protected override void OnModelCreating(ModelBuilder builder)
    {
        // Obrigatório e sempre em primeiro lugar: configura as tabelas do Identity.
        base.OnModelCreating(builder);

        // Relações 1-1 com Morada. Por convenção, uma chave estrangeira sozinha dá uma relação 1-N
        // (a mesma morada podia servir várias unidades). WithOne() diz que é 1-1: o EF Core
        // cria um índice único sobre a chave estrangeira, e cada morada só serve uma vez.
        builder.Entity<Hotel>()
            .HasOne(h => h.morada).WithOne()
            .HasForeignKey<Hotel>(h => h.MoradaId)
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<Reserva>()
            .HasOne(r => r.moradaFaturacao).WithOne()
            .HasForeignKey<Reserva>(r => r.MoradaFaturacaoId)
            .OnDelete(DeleteBehavior.Restrict);

        // (apagar uma categoria apagaria os seus alojamentos). Restrict faz o contrário:
        // a base de dados recusa apagar enquanto houver dependentes.
        // Sem estas linhas, o SQL Server recusa criar a base de dados: de Hotel chegava-se
        // a LinhasReserva por dois caminhos em cascata (pelas reservas e pelos alojamentos).
        builder.Entity<Alojamento>()
            .HasOne(a => a.hotel).WithMany(h => h.alojamentos)
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<Alojamento>()
            .HasOne(a => a.categoria).WithMany(c => c.alojamentos)
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<Alojamento>()
            .HasOne(a => a.modoDisponibilizacao).WithMany(m => m.alojamentos)
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<Reserva>()
            .HasOne(r => r.cliente).WithMany()
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<Reserva>()
            .HasOne(r => r.hotel).WithMany()
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<LinhaReserva>()
            .HasOne(l => l.alojamento).WithMany()
            .OnDelete(DeleteBehavior.Restrict);

        builder.Entity<LinhaReserva>()
            .HasOne(l => l.regimeAlimentar).WithMany()
            .OnDelete(DeleteBehavior.Restrict);
    }
}

Porquê. OnModelCreating é o método onde se configura o modelo por código (Fluent API), quando as convenções e os atributos das classes não chegam. O EF Core chama-o uma vez, ao construir o modelo, e o que lá está entra na migration da Etapa 2. A ficha 5 usa-o para índices únicos e restrições; aqui precisamos dele já, por duas razões.

1. As relações 1-1. HasOne(h => h.morada).WithOne() diz que cada morada serve uma única unidade. O EF Core cria um índice único sobre Hoteis.MoradaId: a base de dados recusa uma segunda unidade com a mesma morada. HasForeignKey<Hotel> diz de que lado está a chave estrangeira, porque num 1-1 não há "lado N" que o indique. O mesmo para a morada de faturação da reserva. A do utilizador fica para a alínea 3.d, depois de o ApplicationUser ter a propriedade morada.

2. As regras de apagar. Numa relação obrigatória, a convenção é apagar em cascata: apagar uma categoria apaga os seus alojamentos. É o que acontece na loja da ficha 3, e a ficha 5 avisa antes de o fazer. No MyHotels as regras de negócio dizem o contrário: uma unidade, uma categoria ou um modo só se apagam sem dependentes (RN05, RN18, RN30), e a morada de faturação nunca se apaga (RN42). OnDelete(DeleteBehavior.Restrict) põe isso na base de dados: apagar com dependentes é recusado.

// Um atributo de validação escrito por nós, para usar como [validarNIF].
// Herda de ValidationAttribute, a classe base de atributos como [Required]
// e [StringLength]. Basta reescrever o método IsValid: recebe o valor do campo
// e devolve sucesso ou uma mensagem de erro, que o formulário mostra.
public class validarNIF : ValidationAttribute
{
    protected override ValidationResult? IsValid(object? value, ValidationContext validationContext)
    {
        if (value == null)
        {
            return new ValidationResult("O NIF é obrigatório.");
        }

        if (value is not long nif || nif.ToString().Length != 9)
        {
            return new ValidationResult("O NIF deve conter exatamente 9 dígitos.");
        }

        // Verificar se o NIF é válido (usando cálculo do dígito de controlo)
        if (!IsValidNIF(nif))
        {
            return new ValidationResult("O NIF é inválido.");
        }

        // Caso seja válido, retorna sucesso
        return ValidationResult.Success;
    }

    // O algoritmo de validação do NIF usado pelas Finanças (módulo 11).
    // O nono dígito é um dígito de controlo, calculado a partir dos oito primeiros:
    // se o cálculo não der o nono dígito, o número não é um NIF válido.
    private bool IsValidNIF(long nif)
    {
        string nifString = nif.ToString();

        // Primeiro dígito do NIF entre 1 e 9
        int primeiroDigito = int.Parse(nifString[0].ToString());
        if (primeiroDigito < 1 || primeiroDigito > 9)
        {
            return false;
        }

        // Calcular o dígito de controlo:
        // somar os oito primeiros dígitos multiplicados por 9, 8, 7, 6, 5, 4, 3 e 2
        int total = 0;

        for (int i = 0; i < 8; i++)
        {
            total += int.Parse(nifString[i].ToString()) * (9 - i);
        }

        // O dígito de controlo é 11 menos o resto da divisão da soma por 11.
        // Se der 10 ou 11, o dígito de controlo é 0.
        int digitoDeControlo = 11 - (total % 11);
        if (digitoDeControlo >= 10)
        {
            digitoDeControlo = 0;
        }

        // O NIF é válido se o dígito calculado for igual ao nono dígito.
        return digitoDeControlo == int.Parse(nifString[8].ToString());
    }
}

// A classe é static: não guarda dados nem se criam objetos dela. Serve só para
// arrumar o método abaixo, que o Program.cs chama em cada arranque da aplicação.
public static class Inicializacao
{

    // Não os cria: é o Program.cs, que chama este método, que os entrega.
    // É async porque cada operação vai à base de dados; o await liberta a thread
    // enquanto se espera pela resposta.
    public static async Task CriaDadosIniciais(UserManager<ApplicationUser> userManager,
                                               RoleManager<IdentityRole> roleManager)
    {
        // Os roles por omissão: os três perfis de utilizador registado.
        // (O quarto perfil, Anónimo, é quem não tem sessão iniciada: não é um role.)
        string[] roles = ["Administrador", "Funcionario", "Cliente"];

        foreach (var role in roles)
        {
            // Só cria o role se ainda não existir. Este método corre em todos
            // os arranques e não pode criar os mesmos dados duas vezes.
            if (!await roleManager.RoleExistsAsync(role))
            {
                IdentityRole roleRole = new IdentityRole(role);
                await roleManager.CreateAsync(roleRole);
            }
        }

        // O utilizador por omissão: o administrador.
        // Aqui é só um objeto em memória; ainda nada foi gravado.
        var defaultUser = new ApplicationUser
        {
            UserName = "admin@localhost.com",
            Email = "admin@localhost.com",
            Nome = "Administrador",
            Apelido = "Local",
            // Só utilizadores no estado Ativo podem iniciar sessão (regras de negócio).
            Estado = EstadoUtilizador.Ativo,
            // O Program.cs exige conta confirmada para fazer login
            // (RequireConfirmedAccount = true). Sem isto, o administrador não entrava.
            EmailConfirmed = true,
            PhoneNumberConfirmed = true
        };
        // Confirma que nenhum utilizador já gravado tem o Id deste objeto novo.
        if (userManager.Users.All(u => u.Id != defaultUser.Id))
        {

            var user = await userManager.FindByEmailAsync(defaultUser.Email);

                // Dá-lhe o role Administrador: uma linha na tabela AspNetUserRoles.
                await userManager.AddToRoleAsync(defaultUser, "Administrador");
            }
        }
    }
